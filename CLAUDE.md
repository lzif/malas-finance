# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**See [AGENTS.md](AGENTS.md).** It is the canonical instruction file for every AI agent working here, and it is kept current. Duplicating it in a Claude-specific file would only let the two drift apart.

Read in this order: `AGENTS.md`, then `spec.md` (the authoritative design), then `TODO.md` (where the project actually is).

## Claude Code tooling preferences

These are specific to the Claude Code CLI/plugin ecosystem and have no equivalent for Gemini/Codex/Cursor — that's why they live here and not in `AGENTS.md`.

- **Caveman mode: always run at `ultra`** in this repo. If a session starts at a lower level, switch with the `caveman:caveman` skill (`args: ultra`). Code, commits, PR bodies, and anything security-relevant still get written in normal English regardless of chat mode.
- **Review delegation:** after any code change, run the adversarial review pass via `agy-bridge --type review --model claude-opus-4-6-thinking` (see the "Review is part of finishing" discipline in `AGENTS.md`) rather than reviewing solo — feed it the relevant spec section, the diff, and an explicit out-of-scope list.
- **Mechanical-task delegation:** when a task decomposes into several genuinely independent, low-judgment subtasks (bulk rewrites, boilerplate scaffolding, repetitive lookups), offload them to `agy-bridge --type implement` or `agy-search` with `gemini-3.6-flash-high` to conserve Claude token budget. Don't force this — a cold flash agent thrashes on tasks needing live environment context (debugging a build, diagnosing CI failures) or on code that's already been written out verbatim in a plan; those stay with the primary agent. Judge fit per-task rather than delegating by default.
- **UI/UX work:** invoke the `ui-ux-pro-max` skill (or its sub-skills — `ui-styling`, `design-system`, `banner-design`, etc.) before designing or reviewing any UI surface — components, color/typography choices, layout, accessibility, charts. Don't freehand UI decisions this repo has a skill for.
- **Manual browser verification (spec §10.4 — "UI verification is done manually in the browser"):** use the `agent-browser` skill/CLI directly. `npm run dev` in the background, `agent-browser open http://localhost:5173/malas-finance/ --args "--no-sandbox"` (sandbox is required in this container), then `snapshot -i` / `click @eN` / `fill @eN`. Two things that cost a round-trip the first time: (1) refs go stale after any click that changes the DOM (delete, tab switch, save) — re-`snapshot` before the next interaction; (2) this app's screens scroll past viewport height, so a click on a ref below the fold silently no-ops — `scrollintoview @eN` before clicking nav buttons and intent buttons at the bottom of Record/History. Don't rediscover browser tooling from scratch each session — this is the answer.
- **Delegate the browser-driving itself to a Haiku subagent.** `agent-browser` sessions are long snapshot/click/screenshot loops — mechanical, no judgment calls, and their raw tool output is pure noise in the main thread. Spawn `Agent` with `subagent_type: general-purpose, model: "haiku"`, hand it the dev server URL plus the two gotchas above verbatim, and ask for a short report back (screen name, elements seen, pass/fail). Verified working: a Haiku subagent drove `agent-browser` correctly first try (open → snapshot → screenshot → close) for ~25k subagent-side tokens, with only the short recap landing in the main thread. Don't drive `agent-browser` yourself when the check is mechanical — delegate it.
- **agy-bridge cannot drive `agent-browser`.** Tested directly: `agy-bridge --type implement` (and by the same tool-restriction, `code`/`analysis`/`review`) refuses any task needing shell execution — its `GEMINI.md` forbids `run_command`. Don't route browser-driving through agy; it can only read/write files, not run CLI tools.
- **When you notice a pattern this section doesn't cover yet — a tool combo that worked, a gotcha that cost a retry, a delegation that paid off — add it here before ending the session.** This file only stays useful if it accumulates; don't let a hard-won discovery evaporate with the conversation.
- **`agy-bridge --type implement` can write into the main checkout instead of your worktree, silently.** Confirmed once: a mechanical delegation asked for 4 files under `src/lib/notify/` and it wrote them to `/home/ubuntu/repos/malas-finance/src/lib/notify/` (the shared main checkout) even though the session's Bash cwd was the worktree — agy's own workspace root isn't necessarily your worktree path. After ANY `agy-bridge --type implement` call that creates/edits files, `ls` the target path in **both** the worktree and the main checkout before trusting it landed in the right place. If it landed in the main checkout, `Read` the files there (read-only is safe) and `Write` copies into your worktree — but the sandbox's worktree-isolation guard will (correctly) refuse to let you `rm` the stray copy from the main checkout yourself. Flag it in TODO.md and the PR body instead; the owner has to delete it.
- **agy's model quota is per-model-tier, and it fails two different ways.** A quota-exhausted call can come back as a silent exit-0 with empty stdout (per the prompting skill's warning) OR as a loud `exit 1` with `Error: Individual quota reached... Resets in <N>h` on stderr — don't assume silence means "nothing to report," check the exit code and stderr explicitly. When a named heavy model (e.g. `--model claude-opus-4-6-thinking`) is exhausted, `agy-bridge --types` shows the default model per `--type` (e.g. `review` → `gemini-*-pro-high`) — omitting `--model` falls back to that default, which may still have quota even when the named one doesn't. It's a real, distinct-model adversarial pass, just not the specific alias CLAUDE.md names by default; say so explicitly in the report rather than presenting it as the standard opus pass. A lightweight probe (`echo "reply PONG" | agy-bridge --type search --model gemini-3.6-flash-high`) is a cheap way to confirm whether the outage is account-wide or scoped to one model tier before spending a real prompt on a call that might just fail again.
- **The owner merges PRs without telling you, at any time.** A commit lands in `main` only if it was on the branch's tip at the moment they clicked merge — pushing again afterward does not retroactively include it. Two habits this forces: (1) before pushing a follow-up commit to an already-open PR, check `gh pr view <n> --json state` first — if it's already `MERGED`/`CLOSED`, open a fresh PR instead of assuming the push still lands; (2) don't trickle small follow-up commits onto one open PR across a long session — batch them into one commit before pushing, so there's no window for the owner to merge mid-stream. This happened once already: PR #7 merged between two of this session's pushes, stranding a commit that needed PR #8 to land.
